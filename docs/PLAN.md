# deltarium-iphone — PLAN

*This app's phases and the immediate next work. Read `docs/SYSTEM_PLAN.md`
first for the whole system.*

## Shape

A teaching iPhone app built Kit-first, mirroring `ham-measure`:

- `EasyModelerKit/` — the pure-Swift ODE engine. Builds and tests on Linux/CI,
  no darwin SDK. This is where the numerics and the fidelity work live.
- `App/` — the SwiftUI + xtool shell (P2, shipped). Sliders, plots, lessons.

## Phases

### P0 — backbone (done at repo creation, 2026-07-25)

Repo scaffolded; doctrine pulled into `docs/doctrine/`; CI hardened; plans
written. `EasyModelerKit` seeded with a fixed-step **RK4** solver (`ODESolver`)
and the **Lorenz** model, plus contract tests (finite/bounded/shaped, and an
`e^{-t}` closed-form fence). `swift build && swift test && swift format lint` all
green. The seed proves the toolchain end to end; it is **not** the real engine.

### P1 — the real engine — shipped ✅

The core numerical work. Deliverables:

- **Adaptive RK45** (Dormand–Prince) with **dense output** for smooth sampling
  between the solver's own steps (the app's plotting layer; the forced model
  itself is handled by per-interval integration with the forcing held constant).
  Keep the pure-`Double`, no-simd discipline so the Linux/iOS bit-identity holds.
- **The three canonical models** as right-hand sides: Lotka-Volterra, Lorenz,
  forced Lotka-Volterra (a time-series `food` input), matching the Python
  definitions.
- **The fidelity oracle.** Export the reference arrays from the Python repo
  (`easymodeler/tests/fixtures/port_reference.npz`, keys `ex1`/`ex2`/`ex3`) into
  a Swift-loadable fixture, and fence:
  - short-horizon agreement to tolerance (the RK45 tracks scipy closely early);
  - qualitative / invariant checks over the full run (bounded attractor, LV
    periodicity, positivity);
  - Lorenz divergence past the Lyapunov time is *expected* — assert the
    early-window match, not the late-window trajectory.
  This is looser than the Python port's bit-exact contract, on purpose (see the
  fidelity note in `SYSTEM_PLAN.md`).
- Calibration / goodness-of-fit stay in the Python engine (tier 2). The phone is
  the interactive toy; it does not need brute-force calibration on device.

**Shipped 2026-07-25 (commit `9300b10`, CI green, 16/16 fences).**
`EasyModelerKit` carries `DormandPrince` (adaptive RK45 5(4) + dense output,
`+ − × ÷` / `sqrt` only, so a run is bit-identical across Linux and iOS),
`ODESolver` (the per-interval reporting driver that mirrors the Python grid), and
the three models. Fidelity fixtures are exported from tier-2 by
`tools/export_fixtures.py` and fenced in `FidelityTests` at *measured* tolerances
(LV whole-run 4.9e-4; Lorenz first-10 7.2e-4; driven-LV first-24 1.3e-4). The
chaotic and near-extinction regimes are fenced for boundedness and positivity,
not a late-window match.

### P2 — the app shell — shipped ✅

**Shipped 2026-07-25 (commit `9b87e75`, CI green).** `App/` is the SwiftUI + xtool
shell (mirrors ham-measure: one library product on `EasyModelerKit`, `xtool.yml`,
`Support/Info.plist`, `Resources/AppIcon.png`). Device target **iPhone only**. The
landing experience is the **predator–prey (Lotka-Volterra) playground** — the
owner's ruling that LV leads as the elegant front door for all users, then the app
branches to the other models:

- Six plain-language sliders re-integrate the engine live into **Swift Charts**,
  two views behind a segmented switch — *Over time* and *The loop* (phase space).
- The front door was refined by a **three-seat design panel** (visual craft /
  motion / invitingness, the house review-panel method): rounded type, an indigo
  accent, a "try this" preset row, warm creature-keyed sliders with value pills, a
  live one-line "story" of the run, material-card depth, and discrete-only spring
  motion with haptics that honours Reduce Motion (the chart never animates on a
  live drag).
- **Time**: a slower · Play/Pause · faster transport runs one wall-clock
  `TimelineView` playhead through both views at once — a sweep with dots over
  time, a travelling dot round the loop — at 0.25×–4×, and it keeps sweeping the
  freshly recomputed trajectory while you drag.
- **Icon**: the app's own classic Lorenz attractor (mirror-symmetrised for
  small-size legibility, lit on a dark ground), generated by `tools/make_icon.py`
  — the real icon, pulled forward from P4.

Open device-tuning carried forward (non-blocking): play performance at 60fps, the
white now-dot contrast, the 4× ceiling, tortoise/hare vs. chevrons.

### P2b — branch the playground to more models

Reuse the playground shell — the home picker, the shared transport, presets, and
the live "story" line — for each further model.

#### P2b-1 — Lorenz, to a device gate — shipped ✅

**Shipped 2026-07-25 (device gate passed).** Owner rulings on the two open forks:
**full SceneKit 3D** for Lorenz (a real attractor you orbit and pinch, over cheaper
2D projections) and **Lorenz first** to a clean device gate, then the food-driven
LV. Delivered, all in `App/` (the Kit is untouched):

- A **home model picker** (`HomeScreen`) now owns the single `NavigationStack` and
  branches to two playgrounds; the app launches there.
- **The Butterfly** (`AttractorScreen` + `AttractorModel`): the Lorenz attractor as
  a live **SceneKit** scene — a self-lit line on a dark stage, orbit + pinch via
  SceneKit's own camera controller — pinned above a scrolling control panel so its
  orbit gesture doesn't fight the scroll. The headline knob is **Chaos (ρ)**, with
  presets walking Calm → On the edge → Classic butterfly (default, the icon) → Wild
  chaos (the tier-2 ρ=99.96 regime); σ/β sit in a fine-tuning card.
- The **butterfly-effect twin**: a toggle starts a second path a hair from the
  first and plays them apart past the Lyapunov time — the teaching beat.
- The transport (play/pause, speed ladder, travelling marker) was **extracted to a
  shared `PlaybackModel` + `TransportBar`**, and the predator–prey screen moved onto
  them — ready for the third model.

Perf/render is kept cheap: the 3D geometry rebuilds only when a parameter changes;
playback just moves the marker node. Device-gate polish carried forward
(non-blocking): SceneKit's 1-px line weight vs. bold tubes, drag-time recompute
cost, and plain-language tuning of the Chaos/Mixing/Settling labels and preset ρ.

#### P2b-2 — the Estuary (open benthos) — shipped ✅

The planned food-driven LV was **superseded**: rather than a second Lotka-Volterra,
the third model became **the Estuary**, an open benthos–nutrient playground built
from the owner's own Benthic Ecology Model (real Rincon Bayou *Streblospio
benedicti* coefficients). Nitrogen is fed in and buried out so it tracks the
seasons; the student feeds the marsh, picks a species, and watches biomass bloom and
crash. Kit `OpenBenthosModel` (grounded against the tier-2 oracle
`easymodeler/examples/bem_open.py`, fenced to tolerance since its `exp` forcing is
not bit-portable), `BenthosScreen` on the shared transport, three real species as
presets, and water-conditions sliders that raise or lower the seasonal salinity and
temperature. Shipped 2026-07-25 (commits `3c2b0a6`, `2d8911e`), CI green.

The driven Lotka-Volterra model stays in the Kit (`DrivenLotkaVolterraModel`) with
its fidelity fence, but has no screen — deprioritized in favour of richer models.

#### P2b-3 — the three-body problem ("The Dance") — shipped ✅

The gravitational three-body problem, the chaos-and-order companion to the Lorenz
butterfly. Owner rulings: the **stable figure-8 choreography** leads as the front
door (beautiful hidden order), chaotic arrangements as presets, rendered in
**SceneKit 3D** so it can be spun. Delivered:

- Kit `ThreeBodyModel` — softened Newtonian gravity, an 18-component state, `sqrt`
  only, so a run is bit-identical Linux↔iOS like the LV/Lorenz models — plus
  `ThreeBodyConfiguration` (the figure-8, Pythagorean, and 3D-tangle arrangements,
  shared by the app and the test) and a `totalEnergy` invariant.
- Tier-2 oracle `easymodeler/examples/three_body.py` and the `three_body.csv`
  fixture. The fidelity story is *inverted*: the Swift DP conserves energy to
  ~1e-10 while the vode reference drifts ~4e-3, so the match is fenced only early
  and the real fence is the conserved energy (on the figure-8 and through the
  chaotic presets' softened close approaches) — four new fences, parity-verified to
  0.0 against the Python oracle before any `swift test`.
- App `OrbitsScreen` ("The Dance"): three coloured trails on the 3D stage, a
  "heavier star" knob that tips the balanced figure-8 into chaos, a ghost-twin
  toggle (locked on the stable 8, drifting off in the chaos), the shared transport,
  and the home-picker card.

**Shipped 2026-07-25 (commit `1317b1c`, CI green, `swift test` 22/22, device-gated).**
Device-tuning carried forward (non-blocking): the SceneKit 1-px trail weight, the
star-colour palette on the black stage, camera framing as arrangements resize, and
the heaviness range before a star ejects.

#### P2b-4 — the Earth–Moon Lagrange points ("Parking in Space") — built, awaiting the gate

The circular restricted three-body problem (CR3BP): Earth and the Moon fixed in the
rotating frame, and the five Lagrange points where their gravity and the centrifugal
pull cancel. Owner rulings: the **rotating frame** (so Earth/Moon and the points sit
still and stability reads at a glance) and **five satellites at once**, one launched
from each of L1–L5, sharing the delta-v the user dials. Delivered:

- Kit `RestrictedThreeBodyModel` — the CR3BP equations, a 6-component state, `sqrt`
  only (bit-identical Linux↔iOS) — plus `EarthMoonSystem` (μ and the five Lagrange
  points, L1–L3 by Newton, L4/L5 exact; shared by the app and the test) and the
  `jacobiConstant` invariant.
- Tier-2 oracle `easymodeler/examples/lagrange.py` and the `lagrange.csv` fixture.
  Same inverted-oracle story: the Swift DP holds the Jacobi constant to ~1e-15 while
  the vode reference drifts ~2e-6, so the real fences are the Jacobi invariant, the
  fact that every Lagrange point is a machine-precision equilibrium, and the
  stability contrast (L4/L5 hold, L2 escapes) — four new fences, parity-verified to
  0.0 against the Python oracle.
- App `LagrangeScreen` ("Parking in Space"): Earth, the Moon, and the five points on
  a fixed 3D stage, five coloured satellite trails, three delta-v sliders (toward
  Moon / along orbit / out of plane) with still/nudge/hard-kick presets, the shared
  transport, and the home-picker card.

Gates green (Kit build + build-tests + lint; App `xtool dev build` + lint). **Not yet
run: `swift test` and the device gate — the owner's calls.** Device-tuning to flag:
the fixed frame extent, the satellite and target marker sizes and colours, the
delta-v slider ranges and default kick, and the escaping satellites' close-approach
performance.

#### P2b-5 — radioactive decay ("Radioactivity") — built, awaiting the gate

The simplest ODE in the system (`dN/dt = −λN`) and the first **2D** playground — a
decay curve on Swift Charts. Owner's design: a radiation trefoil, the title
"Radioactivity" and the question "how long does it take for radioactivity to dissipate
in the environment naturally?", a source selector (Carbon-14 dating / reactor accident
/ H-bomb), and distance and concentration sliders. Owner's key correction: **a nucleus
doesn't just vanish — it decays into a daughter that is usually radioactive too**, so
this is the Bateman decay-chain model and the activity lingers down the chain. Rulings:
model the plutonium/uranium chain to its **key long-lived members** (folding the
ultra-fast daughters in by secular equilibrium so it isn't stiff) and give each source
a **per-source linear time window**. Delivered:

- Kit `DecayChainModel` — the coupled linear decay ODE (`−λN` out of each member,
  `+λN` into its daughter), `+ − ×` only, so a run is bit-identical Linux↔iOS — plus
  `RadiationSource` (the three sources' chains, half-lives, and the activity weights
  that fold in the fast equilibrium daughters; shared by the app and the test).
- Tier-2 oracle `easymodeler/examples/decay.py` and the `decay.csv` fixture (the
  actinide chain). Most fences are exact and need no oracle: atoms are conserved to
  ~1e-15 (decay transforms nuclei, never destroys them) and every parent halves to
  `e^{-ln2}` after one half-life; the fixture pins the multi-member ingrowth. Four new
  fences, parity-verified to 0.0 against the Python oracle.
- App `RadioactivityScreen` on Swift Charts: the trefoil + title + question, a source
  segmented picker, the activity-vs-time curve with a "safe background" line and a
  "safe after ~X years" readout, distance/concentration sliders (accident and bomb),
  and the shared transport. `RadiationSymbol` draws the trefoil as vector art.

Gates green (Kit build + build-tests + lint; App `xtool dev build` + lint). **Not yet
run: `swift test` and the device gate — the owner's calls.** Device-tuning to flag: the
linear y-axis hides the H-bomb's faint uranium floor (log-y would surface it) and the
iodine's brief initial spike; the safe-line level; the distance/concentration ranges;
and the trefoil and curve colours.

#### P2b-6 — build your own system ("Build Your Own") — built, awaiting the gate

The other models are fixed equations; this one hands the equations to the user —
"where the app earns its keep for learning." Owner rulings: the classic-EasyModeler
equation shape (modernized, not literal `emlib` syntax), coefficients as **sliders**
(with a type-to-set value field), and a bounded ceiling — **up to 6 boxes** (state
equations and user-editable inputs sharing the budget) and **15 coefficients**; past
that, the honest answer is the full Python engine (tier 2). It opens pre-loaded on
the **Benthic Ecology Model** (the owner's 2016 code) to remix, and plots in **2D**
on Swift Charts. Delivered:

- Kit `Expression` — a lexer and recursive-descent parser for `+ - * / ^`,
  brackets, and the functions exp / ln / log / log10 / sqrt / abs / pow / sin /
  cos / tan / min / max — and `ExpressionSystem`, which validates named states,
  inputs, coefficients, and ordered helper expressions and wires them into the
  same `ODESystem` the built-in models use. Fidelity mirrors the rest: a system
  typed with only `+ - * /` is **bit-identical** to a hand-written right-hand side
  (the parser reproduces the operation order), while `exp`/`pow` systems carry the
  tolerance contract. Seven new fences, including LV-from-text and Lorenz-from-text
  matching the hand models bit for bit and a helper/`exp` system matching its
  inlined and hand-written forms; the built-in models are themselves
  Python-verified, so the match is transitive. `EasyModelerKit.version` → 0.2.0.
- App `BuildScreen` + `BuildModel`: the chart (one coloured line per state) on the
  shared transport, a **States / Helpers toggle** (the helpers carry different
  units, so they read on their own axis via the Kit's `helperValues`), editable
  equation and helper text with live parse feedback (a typo holds the last good run
  and names the problem in plain language), input and coefficient sliders with a
  type-to-set value field, add/remove within the caps, a time-span slider, and
  four starter systems to remix — Estuary/BEM, predator-prey, Lorenz, and an empty
  **Scratch** to build from nothing.

Gates green (Kit build + build-tests + lint; **`swift test` 36/36**; App
`xtool dev build` + lint). **Not yet run: the device gate — the owner's call.**
Device-tuning to flag: the per-frame chart redraw at up to six lines during
playback (the `sampleCount` knob), the raw text-field equation editor vs. a custom
math keypad, name-field validation, and the coefficient slider ranges.

#### P2b-7 — Time Dilation, plus the Guided Tour skeleton — shipped ✅

The eighth world: a relativistic interstellar journey at constant g-force
(flip-and-burn), integrated over the ship's proper time, with a 3D spacetime
worldtube that grows as the rocket flies (its girth tracks 1/γ, ribbed at
ship-clock ticks), two clocks (Earth vs. ship), nine real destinations from Alpha
Centauri to TON 618, and an astrophage fuel gate. Kit `RelativisticJourneyModel`
plus six fences (`swift test` 43/43); tier-2 oracle
`easymodeler/examples/relativity.py`. A **Guided Tour** learning-path skeleton
sits at home-screen slot #2 (content still to be written). The app was renamed
**Deltarium** (the Python package stays EasyModeler).

### P3B — AR projection of the model (investigation)

*Owner idea (2026-07-25): project the graph into **augmented reality** as a
teaching method for the single LV model.* Investigate rendering the dynamics in
real space — the phase-space loop or the populations as a 3D object a student can
walk around and place on a table, and later the Lorenz attractor floating in the
room. **The toolchain is proven**: `ham-measure` is an ARKit/RealityKit app built
and signed on this same xtool-from-Linux lane with its device gate passed, so
ARKit-under-xtool links and runs. To decide in a research spike (like the Phase-3
front-end research on the Python side): which quantity to project (phase loop vs.
attractor vs. a timeseries surface), the interaction (walk-around, place, scale,
play the same time transport in AR), and whether AR is a mode inside the LV
playground or a separate screen. Keep AR code quarantined in `App/` — ARKit never
enters the Kit — mirroring ham-measure's shell/Kit split.

## Open decisions

- **Device target — settled: iPhone only** (owner ruling 2026-07-25; no toolchain
  capacity for an iPad target). The P2 app shell targets the iPhone device family
  only. Recorded in `SYSTEM_PLAN.md`.
- **Solver — settled: Dormand–Prince RK45** (P1). scipy does not build for iOS, so
  the engine is a Swift-native adaptive solver; matching scipy's `vode`
  bit-for-bit is *not* a goal — short-horizon tolerance is the contract.
- **CI breadth.** Currently one hardened Linux job. A `macos-latest` parity job
  (as in ham-measure) can be added when the fidelity work lands, to catch any
  iOS-ARM float divergence early.
